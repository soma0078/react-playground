# /motion

사용자는 수치를 말하지 않는다. **일상어 요청 → 구현 → 고칠 말 → 다시 구현**으로 수치를 정하고,
요청에 쓴 말과 최종 수치를 어휘집에 짝지어 남기는 것이 이 스킬의 목적이다.
`spec.md`에는 사용자의 말이 아니라 **한 번에 같은 결과를 만들 수 있는 프롬프트**를 남긴다.
흐름 전체는 `docs/WORKFLOW.md`, spec 형식은 `src/motions/README.md`를 따른다.

## 무엇을 하는 요청인지 먼저 가른다

| 사용자의 말                                        | 할 일                        |
| -------------------------------------------------- | ---------------------------- |
| 새로운 움직임 묘사 (`/motion …`, "~하게 만들어줘") | [A. 새 요청](#a-새-요청)     |
| 변형 이름을 고름 (변형 탭이 있을 때)               | [B. 고르기](#b-고르기)       |
| 결과를 보고 고칠 말 ("더 세게", "너무 빨라")       | [C. 수정 요청](#c-수정-요청) |
| "채택", "좋아 이걸로"                              | [D. 채택](#d-채택)           |
| "거절", "별로야, 빼줘"                             | [E. 거절](#e-거절)           |

어느 모션 얘기인지 불분명하면 가장 최근에 만든 `status: proposed` 항목으로 본다.
그래도 둘 이상이면 그때만 묻는다.

## A. 새 요청

1. **읽는다**: `src/motions/README.md`, `vocabulary/*.md`, `taste.md`, 기존 `src/motions/*/spec.md`.
   거의 같은 모션이 이미 있으면 새로 만들지 말고 그 항목에 [C. 수정 요청](#c-수정-요청)으로 붙일지 묻는다.
2. **요청을 프롬프트로 옮긴다.** 사용자의 문장을 그대로 남기지 않는다. 해석한 내용을 **일상어에 가까운
   2~4문장(220자 이하)**으로 쓴다. 무엇이 어떤 느낌으로 움직이는지만 쓰고, 수치는 결과를 크게 좌우하는 것
   **최대 2개**만 넣는다. 용어는 개발자가 쓰는 표준 용어로 쓴다 (skeleton → 스켈레톤, shimmer → 쉬머, toast → 토스트). 직역 금지. 나머지 값 · 시간은 `## 수치`로 보낸다 (요청에 수치를 나열하지 않는다)
3. **해석한다.**
   - 요청에 쓰인 말이 `feel.md`에 **확인됨**으로 있으면 그 수치를 기본값으로 쓴다
   - 없으면 `triggers` · `properties` · `timing`에서 가장 가까운 조합을 고른다
   - `taste.md`의 거절 사유에 걸리는 방향은 피한다
4. **데모는 하나만 만든다.** 요청에서 가장 모호한 축(대개 세기나 속도)은 상수 하나로 모으고,
   그 상수에 "어느 쪽으로 바꾸면 어떻게 되는지" 주석을 단다 (예: `1 빠름 · 2 보통 · 3 느림`).
   변형 탭(`## 변형`)은 사용자가 비교를 원할 때만 만든다
5. **파일을 만든다** (`src/motions/<slug>/`, slug는 영문 kebab-case):
   - `spec.md`: `origin: human`, `status: proposed`, `created: <오늘>`, `preview`, 어휘집 키로 된 태그. 섹션은 요청 · 수치 · 메모. frontmatter `hooks:`에 구현에 쓴 framer-motion 훅을 적는다
   - `Motion.tsx`: 한 파일로 완결. 쓸 수 있는 것은 `react`, `framer-motion`, `lucide-react`, `@/lib/utils`의 `cn`뿐. **새 의존성 추가 금지.**
     수치는 이름 붙인 상수로 파일 위쪽에 둔다
   - **주석은 최대한 짧게, `~음` · `~임` · 명사로 끝낸다** (예: `// 글자 가독성용 어두운 막`).
     핵심 모션을 조절하는 상수 · 코드에는 반드시 주석을 달아 무엇을 바꾸면 어떻게 되는지 적는다
   - scroll-linked는 `useTransform` 입력 구간을 `[0, …, 1]`로 끝까지 명시한다 (`vocabulary/triggers.md` 구현 주의)
   - `demo.tsx`: default export 하나. 변형 탭을 만들 때만 `MotionDemoProps`의 `variant`를 받는다
   - 참고 구현: `src/motions/scroll-expand-hero/` (변형 탭 예시는 `magnetic-button/`)
6. **어휘집을 맞춘다.** 표에 없는 키를 태그로 썼으면 해당 파일 표에 추가한다.
   `feel`에 새 말을 넣었으면 `feel.md`에 **가설**로 추가한다 (수치 필수).
7. **검증한다.**
   ```bash
   npx prettier --write src/motions/<slug> vocabulary
   npm run spec:check -- <slug>
   npx tsc -b && npm run lint && npm run build
   ```
   가능하면 `npx vite preview --port 4799 --strictPort`를 띄우고 headless Chrome으로
   `/motions/<slug>`를 캡처해 화면을 직접 본 뒤 서버를 끈다.
   스크롤 연출은 0 → 100% → 다시 0까지 전 구간을 샘플링한다. 중간 지점만 보면 끝 구간 버그를 놓친다.
   수정 요청이 무엇을 가리키는지 애매하면 추측해서 고치기 전에 지금 버전을 그 구간까지 재현해 본다.
8. **보고한다.** 확인할 주소(`/motions/<slug>`), 요청의 어떤 말을 어떤 수치로 읽었는지,
   조절 상수를 바꾸면 어떻게 되는지 한 줄. 이어서 "고칠 말을 한 줄 주세요"로 끝낸다.

## B. 고르기

frontmatter에 `chosen: <변형 이름>`을 적는다. `status`는 그대로 둔다 (고르기 ≠ 채택).

## C. 수정 요청

1. 그 말에 맞춰 구현과 수치를 고친다
2. `## 요청` 프롬프트를 고친 결과까지 담아 **다시 쓴다** (줄을 덧붙이지 않는다. 같은 한도: 2~4문장, 수치 최대 2개)
3. `## 메모`는 최종본 기준으로 짧게 정리한다. 시행착오 경위는 남기지 않고, 다시 만들 때 필요한 주의점만 남긴다
4. A의 6~8을 다시 한다

## D. 채택

1. `status: adopted`. 변형 탭이 있는데 고른 것이 없으면 지금 보이는 변형을 `chosen`으로 적고 그렇게 했다고 알린다
2. `feel.md`: 대화에서 사용자가 쓴 느낌 표현 ↔ 최종 수치를 **확인됨**으로 적는다.
   같은 뜻의 줄이 이미 있으면 새 줄을 만들지 말고 그 줄에 표현을 덧붙인다
3. `taste.md`: `- <오늘> · <slug> · 채택 · <이유>`. 이유를 말하지 않았으면 `이유 미기재`
4. 사이드바 NEW 배지는 status를 따라 자동으로 사라진다

## E. 거절

`status: rejected`, `taste.md`에 `거절` 한 줄. **파일은 지우지 않는다** (갤러리 목록에서만 빠진다).

## 지킬 것

- **spec에 사용자의 문장을 그대로 남기지 않는다.** 사용자가 쓴 느낌 표현은 `feel.md`에만 남긴다
- **커밋은 사용자 확인 후에만.** 브랜치는 `feature/motion-<slug>`, 같은 모션의 후속 변경은 `--amend`
- 커밋 · PR 본문에 `claude.ai/code/session` 링크를 넣지 않는다
- 작업은 로컬에서만 한다. 클라우드 실행 · 발행을 쓰지 않는다
- 라우터 · `nav.ts`는 건드리지 않는다. 폴더만 추가하면 자동 등록된다 (`src/motions/registry.ts`)
